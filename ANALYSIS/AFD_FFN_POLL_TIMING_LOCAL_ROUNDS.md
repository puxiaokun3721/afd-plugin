# A5 AFD 轮询时间戳与 Attention 独立分轮分析

本次处理两个独立的问题。FFN Poll 要提供该卡首次看到每个成员 Ready 时的设备系统周期。Attention 成员按本地发送行数分轮时，第 0 轮仍按同一个 DP 的完整成员集合确认，后续轮等尚未发完的成员。接口、内存和约束见 [事务设计第 11 节](../docs/design/a5_afd_ffn_transaction.md#11-poll-设备时间戳与-attention-成员独立分轮)。

## 同一个 DP 的成员可以有不同发送行数

当前普通 TP 接 CAM 时先把 token 轴补齐到 TP 的整数倍，等长分片，发送行数取本地张量尺寸。vLLM 的序列并行切分也采用先补齐再等分的方式。原始有效 token 的差异可以保留在有效性标记中，共同轮数可由同一个补齐长度直接算出。vLLM 的预填充上下文并行有另一种情况，PCP 源码会得到不同 rank 的有效行数，再按最大本地行数补齐各卡的输入。若以后只把有效行数传给 DS，各成员本地最少轮数可能不一样。现有 AFD NPU ModelRunnerV2 要求 PCP 和 DCP 均为 1。下面验证的是低层事务协议。 [CAM 等长切片](../afd_plugin/model_executor/models/npu/async_cam_layout.py#L188) · [vLLM PCP 切分](https://github.com/vllm-project/vllm/blob/ced6857afa0ea7b2e3f0846a62e1394e90f15607/vllm/v1/worker/gpu/pcp_manager.py#L298) · [AFD 平台限制](../afd_plugin/validation.py#L126)

## 一个跨容量边界的例子

以下是 `H=7168`、BF16 的建议验收输入。一个 DP 有 A0、A1 两个成员，每源一槽。表中取 `C=32768`，A0 有 32,769 行，A1 有 32,768 行。首跑用 `C=8192`、A0 8,193 行、A1 8,192 行和 `Q=Q_alloc=16384` 验证同一边界。表中事件是验收期望。

| 事件 | 共同轮数 | 成员独立分轮 |
|---|---|---|
| 两张 A 填任务 | 本地行数分别为 32,769 和 32,768，共同轮数均为 2 | 两张 A 分别声明本地轮数 2 和 1 |
| FFN 第 0 轮 | 等齐 A0 和 A1，再从两张 A 取实际路由 | 同样等齐，F 保存两张 A 的轮数声明 |
| FFN 确认第 0 轮 | 对两张 A 发 Done／Consumed；每张 A 的 CR 逐 F 接收并回写 Credit | 同样确认两张 A。A1 的本地任务已结束，可以在原槽发布不同 MB ID 的新任务 |
| FFN 第 1 轮 | 等 A0 的 1 行及 A1 的 0 行控制轮。两张 A 均需要第 1 轮确认和 Credit | 只等 A0 的 1 行，A0 独立完成该轮的确认和 Credit |
| 新任务第 0 轮 | 两张 A 等各自的旧任务完成后发新任务 | F 可同时看到 A0 的旧任务尾轮和 A1 的新任务首轮，各按自己的任务身份判断到齐 |

两种方案都以原轮内 token 和 TopK 槽寻址回包。差别在于每一轮的参与成员集合。共同轮数使 F 每轮都可以用同一份成员表判断，短卡用空轮满足集合条件。独立分轮把成员集合放在每个 F 本卡保存，省去短卡空尾轮及其确认。零路由的 F 仍要给本轮每个实际参与的 A 发信号。所有 F 确认 A1 自己的最后一轮，才说明 A1 可复用槽。A0 旧任务尾轮仍由其自己的确认推进。

旧、新任务可能同时出现，因此跨轮状态要与槽中的当前 Inbox 解耦。同一个 `(DP, phase, MB, layer)` 在旧任务的所有尾轮退役前不得重用。本次用不同 MB ID 明确区分新旧。验证提前复用时，先通过本轮轨迹证明 A1 完成旧任务，再观察 A1 新任务 Ready 在 A0 旧尾轮退役前出现，最后核实两份数据各自收回正确位置。单测可覆盖重复声明和错误轮号，设备报告须注明控制注入方式。

## Poll 等待时间的两个口径

在同一个 F 上，先后看到 A0 和 A1 Ready 时分别采集 `t0` 和 `t1`。后续 Scheduler 若读到 `now`，可以使用 `now - min(t0,t1)` 表示首个成员已经等了多久，或者使用 `now - max(t0,t1)` 表示本轮成员都被看到后又等了多久。成员独立分轮时，只在该轮实际参与的成员间计算这两个值。用于排序的 Credit 资格可能在 Ready 后才成立，若要测量它需要另外定义事件。

这里交付的是每 lane 的 64 位原始设备系统周期。时间随发布代次保存。反复看到同一代时周期应不变，下一代出现后才更新。Scheduler 可能在两次 Poll 之间先接管某次发布，读取者须核对记录身份并处理缺失。诊断脚本的 Host 调用耗时只统计 Poll 提交、读回等操作。工作负载间隔会影响两次观测之间的窗口，因此报告内写明 Poll 的调用位置。测试脚本或上层读取者应保留原始周期和有效标记，确认两次设备读取来自同一 F 上可比较的计数器。

## 实机验收记录

- 先用单卡 CAM `H=7168` 验证时间戳首次写入、重复 Poll 不改值、下一代写新值和同卡设备周期差。记录经过的真实 AOT/JIT 路径及加载文件。
- 四卡用两张 A、两张 F 验证共同轮数和独立分轮，记录两条 lane 的 Ready、首轮冻结成员、每轮入选、真实 CS、逐成员 Done／Consumed、A 的账本和 Credit。如果另一张 F 只有控制流程，也应在它的日志中核对握手。
- 四卡加入全空首轮和短成员同槽下一 MB。分别核对共用轮数下的空尾轮、独立轮数下的参与成员列表，以及两份带可辨识输入的逐元素基准结果。
- 用独立测试覆盖非法轮数、混合分轮模式和身份冲突。保留 CPU、驱动下的 CANN 构建、A5 实机三类结果。所有实机输入均用 `H=7168`。
